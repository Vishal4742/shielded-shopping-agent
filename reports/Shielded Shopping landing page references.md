# Make Shielded Shopping Clear and Credible

The strongest direction for the Shielded Shopping Agent page is a short, concrete purchase story backed by a precise privacy map. Keep the site informational and hand off purchases to Telegram; show one request, quote, confirmation, top-up result, and shielded receipt. Use Zcash’s plain-language explanations, Telegram’s message-bound actions, and Bitrefill’s clear product flow as references. One copy issue needs resolution before publishing: the hero says only the user’s viewing key can read receipts, while the threat model says the operator holds user seeds and can inspect user data. **Correction:** the earlier review treated the fictional Tiffin Pass style test as the product; this report is grounded in the SSA repo and requirements.

## Lead with one purchase and one Telegram action

The first screen should answer what the bot buys, what funds it, and where the purchase happens. A direct headline such as “Buy a Jio, Airtel, or Vi top-up with shielded Zcash in Telegram” covers the product without implying the web page can transact. Give “Open in Telegram” the primary button, with a short demo as the secondary action. This follows Zcash’s separation of “Use Zcash” and “Learn Zcash” and Bitrefill’s concise product → pay → receive explanation ([Zcash](https://z.cash/), [Bitrefill](https://www.bitrefill.com/)). Keep “Testnet · invite-only · operator-managed wallet” close to the action; the SRS requires an informational page, QR, judge instructions, caps, and a repo link, while excluding web purchasing ([SRS FR-15](../docs/03-srs.md)).

Show one clearly marked sample chat card below or beside the hero. Telegram recommends inline buttons for actions tied to a specific message, and its Bot API allows the bot to edit the quote message as its state changes ([Telegram bot guidelines](https://core.telegram.org/bots/guidelines), [Telegram Bot API](https://core.telegram.org/bots/api)). Use that to illustrate the real flow: quote with INR, ZEC, fee, expiry, and masked phone → Confirm / Cancel → Buying → Delivered, Failed, or Checking. Label the animation “Demo” and stop it offscreen; a scripted success should never look like a live purchase.

## Make privacy accurate before making it visual

The privacy explanation should name five viewers: **public chain, Bitrefill, Telegram, operator, and user**. Zcash’s own pages explain shielded transactions in plain language and distinguish them from transparent activity ([Zcash traceability explainer](https://z.cash/learn/is-zcash-traceable/), [addresses and value pools](https://zcash.readthedocs.io/en/latest/rtd_pages/addresses.html)). Zodl’s benefit-led sections show how to organize topics like privacy and shielded notes, but its self-custody and no-tracking claims do not fit this custodial demo ([Zodl](https://zodl.com/)).

Resolve the repo’s own claim first. The threat model says the operator holds all user seeds and can see orders and phone numbers; it also says Bitrefill sees the top-up phone and amount, while Telegram handles the conversation ([threat model §§1, 4](../docs/07-threat-model.md)). Replace “Only your viewing key can read the receipts” with wording scoped to public-chain visibility, then disclose the operator’s access beside the receipt demo. A viewing key is read-only but exposes transaction data; the Zcash Foundation describes that distinction, and the Zcash glossary frames it as selective disclosure ([Zcash Foundation](https://zfnd.org/introducing-blockchain-scanning-with-zebra/), [Zcash glossary](https://zcash.readthedocs.io/en/latest/rtd_pages/glossary.html)). The bot’s `/viewkey` message should carry the same warning. The difference between a view key and a user-exclusive view matters because the operator has wallet seeds in this design.

## Let one receipt explain the shielded difference

Make the receipt the centerpiece instead of adding another general privacy paragraph. Use the same sample order in a small “View as” control: public chain, Bitrefill, Telegram, operator, user. Highlight the fields each party sees, and label the sample as simulated. Privacycoins.io explicitly marks its privacy comparison as a demo rather than real decryption, a useful cue for separating illustration from cryptographic proof ([Privacycoins.io](https://privacycoins.io/)). The Zcash wallet UX checklist also emphasizes keeping memo fields visible in wallet transactions ([Zcash Feature UX Checklist](https://zcash.readthedocs.io/en/latest/rtd_pages/ux_wallet_checklist.html)).

Keep claims tied to what the implementation can demonstrate. The repo’s planned memo includes order reference, operator, and rupee amount; a txid alone should not be presented as public proof of a shielded payment. ZIP 311 remains a draft and leaves receipt-validity UI questions open ([ZIP 311](https://zips.z.cash/zip-0311)). Show the actual memo shape only after the `list-tx` parsing behavior has been verified in Phase 0 (§3.5 of the detailed design).

## Make the judge path and stats easy to scan

After the product and privacy proof, give judges a compact path: get an invite at the table → open or scan the bot → `/start <code>` → use the pre-funded demo wallet or deposit. Keep a repo link and a short demo video nearby. Hackathon showcase pages such as ZecHub and ETHGlobal use a short description followed by a video, live demo, or source link, so visitors can move from pitch to proof without reading a long page ([ZecHub results](https://zechub.substack.com/p/zechub-hackathon-results-are-in), [ETHGlobal Hidden Garden](https://ethglobal.com/showcase/hidden-garden-iek02)).

Keep the stats panel to the three FR-16 measures: delivered top-ups today, rupees committed against the ₹200 cap, and shielded receipts. Put “Zcash testnet demo” and “updated N seconds ago” beside them; use the specified paused and offline states instead of stale or fabricated counts. ZecZcash’s shielded-supply tracker is a useful reference for naming a metric, timestamping it, and explaining what it does not measure ([ZecZcash tracker](https://zeczcash.com/shielded)). Do not borrow its network-level statistics as SSA data. The threat model also records that rapid live updates can reveal an in-room purchase’s amount and approximate time; if the team changes that exposure, update the requirements and threat model before changing the panel.

## Preserve the visual system and reduce competing motion

The existing design direction already has a coherent riso hero, dark body, cobalt footer, self-hosted fonts, and one receipt interaction. Keep those choices, but let the purchase chat and receipt carry the story; the scan reveal, count-up stats, decoding fields, moving tagline, and chat loop can compete if all run together. The prior research recommends one hero entrance, at most one loop, and scroll reveals that stop offscreen ([design research](../notes/design-research.md)). Use a one-column mobile flow with the Telegram CTA visible before the chat card, and check contrast, focus rings, reduced motion, and horizontal overflow against the design spec’s desktop and mobile checks (§10.5 of the [detailed design](../docs/05-detailed-design.md)). The page must remain tracker-free and self-host its assets under FR-15.

## Conclusion

The clearest improvement is not a new visual theme; it is a tighter chain of evidence: product → quote → confirmation → delivered top-up → shielded receipt, with each privacy boundary named honestly. Resolve the operator/viewing-key contradiction and the accepted live-stats timing disclosure before polishing the copy, then use one sample order to make the page’s visuals, Telegram demo, privacy explanation, and stats feel like parts of the same product. These references inform presentation only; they do not verify SSA’s wallet behavior, security, merchant integration, live metrics, or privacy claims.
